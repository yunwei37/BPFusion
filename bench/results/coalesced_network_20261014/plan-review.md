## Driver executability, cancellation and lifetime

The current io_network is not a stateless iteration: io_uring_tcp.h:74–81 initializes connection links, free/active/accepting indices, connection count, seen/next_final, stopping/cancelled/cancel_done, timeout_active/timeout_removing and eight IoRequest records as kernel-local state. Its CQ processing mutates them, including partial sends, ordered retirement, generation tags and cancellation completion. All of that state must survive each dispatcher invocation and tail launch. Preserving only IoConn and IoStats is insufficient. The ring/buffer addresses, listener/capacity and host-address fields must also remain valid until the drain completes. Initialize once; neither each step nor the shutdown worker may reset the state, pending timeout ownership or connection/request links.

The extracted step must finish/return when cancellation awaits a future CQE. Copying the current stopping&&!cancel_done nanosleep/continue as a private infinite wait would stop the dispatcher from completing its model/stop lifecycle. Conversely, returning prematurely from the whole network lifecycle or setting loop.finished merely because one step has no work would release live io_uring references. CQEs must remain drained before buffer reuse/new publications; multishot timeout F_MORE CQEs must not decrement the one pending timeout ownership until the final CQE. Keep current final/abort admission ordering, receive-cancel/close ordering, generation/tag checks and system-scope synchronization.

Run progress on the existing dispatcher's idle/reclamation/admission path as well as after model outputs. If progress is conditional only on a completed model graph, initial ACCEPT/RECV can never admit the first request; when no model work is eligible, pending sends/final reclamation also need progress. The qwen dispatcher executes one thread and tail-resumes after child graphs; the vLLM dispatcher can additionally appear inside combined body/head graphs under BF_CHAINED_DISPATCH. Network pointers/state must be initialized before these graph parameter copies/instantiations, or updated consistently through the real CUDA graph API before root launch. Verify the chosen baseline/candidate compile flags retain the same current packing, prefix release and graph scheduling policy.

The existing shutdown order is model stop -> cudaStreamSynchronize(0) -> model_quiesced -> uring_drain -> device/network synchronization -> io_uring teardown (qwen_graph.cu:183–191, vllm_graph.cu:260–268). Coalescing removes the worker that currently stays alive across model synchronization. The replacement must launch the existing drain worker only after the model stream, its fire-and-forget descendants and tail launches are quiescent, on the same durable state. Then the original host uring_drain must keep entering the kernel loop while the GPU processes cancels/receives/closes/timeout removal. Waiting on that GPU drain stream before entering DEFER_TASKRUN would deadlock deferred completion work. This follows directly from SINGLE_ISSUER|DEFER_TASKRUN and bpf/uring_loop.bpf.c:18–36: after model_quiesced, stop/deadline no longer ends the kernel loop, and it drains until GPU finished. Only after that terminal event may ring, mapped buffers, page, connection/request state and graph controls be freed.

The 60us existing multishot timeout continues to produce activity while a model graph runs, whereas a coalesced step cannot service its CQ concurrently. This is a real changed liveness/backpressure exposure, not grounds to speculate about a failure or change the timer. Check the existing dropped/overflow/pending/SQ/CQ terminal diagnostics and actual strict/idle/inflight-stop behavior. Preserve a stall/overflow as failure. If qualification needs a timer/queue/protocol change, that is a recorded material intervention deviation, not silent scope-preserving repair.
