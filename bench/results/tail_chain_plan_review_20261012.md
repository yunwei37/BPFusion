## Source executability and mechanism engagement

The inspected candidate appends the existing dispatcher as a kernel dependent on the complete head child graph. It allocates queue/device/control/metadata pointers before graph instantiation, uploads all executable graphs and synchronizes before the initial host submission. It uses one chosen-graph tail launch; the separate branch still fire-and-forgets model work and separately tail-launches the current dispatcher. Query-zero aliases retain their existing query-one graph handles. When the chosen graph is the current graph this is a tail self-launch, rather than a prohibited overlapping launch. One dispatcher invocation enqueues at most one next tail launch. Shutdown sets the stop flag, synchronizes graph execution, and only then releases memory/graph resources.

The official [CUDA graph documentation](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/cuda-graphs.html#tail-launch), opened during review, specifies completion of a graph environment before tail work runs and permits one pending self-tail launch. These semantics support the proposed dependency/lifetime design, but hardware/runtime eligibility and absence of actual graph errors still require the real preflight. No separate steady host scheduler was added.

The native successful-call counter is incremented only after cudaGraphLaunch success. The driver checks separate=2 x model_steps and chained=model_steps; analysis additionally compares traced model_steps with actual compute event count. This is appropriate mechanism engagement for the intended change, rather than proof that every saved launch translates into a performance gain. In untraced timing it is only aggregate counter/source-mode evidence; do not manufacture per-cell mechanism observations.

The new CLI comparison is mutually exclusive with packing/release comparisons. Its condition-to-binary mapping and analyzer paired mode names match the plan. Commands use existing source-native benchmark/analysis paths and temporary official runtime construction. Exact model paths/environment/build commands remain to be recorded by execution, as planned. A build or first run failure can be repaired within the stated contract while retaining raw failure/deviation evidence; none is assumed absent by this review.

## Metrics, repetition, completion and interpretation

The official [vLLM metrics documentation](https://docs.vllm.ai/en/v0.31.0/design/metrics/), opened during review, defines TTFT and per-request TPOT. The project client measures complete token arrivals from send start; its TTFT includes TCP/client effects and is not numerically identical to vLLM's internal frontend timer. The current driver records raw start/arrival timestamps, computes TPOT from first-to-last over gen-1, and throughput from whole-cell first send to last delivery. These ordinary client definitions and existing complete recomputation are suitable for the declared matched A/B. Server-side timer interpretations must remain separate.

The full matrix arithmetic is consistent: two models x four conditions x four gen/concurrency cells x five process blocks = 40 executors/160 cells/10240 measured requests/332800 measured tokens, plus 320 checked gen1 warmups excluded from timing. The rotating/reversing existing four-condition order distributes temporal exposure; it cannot prove host/GPU isolation or eliminate drift. All raw samples/outliers, co-tenant endpoints and bounded journal evidence must stay visible.

The eight primaries are unambiguously two metrics x two transports x two models: gen1/c1 TTFT and gen64/c8 throughput, chained versus separate. Five process blocks, not pooled requests, are the paired units. Nominal two-sided t95 df4 estimates are reasonable scoped exploratory evidence with only five blocks; they are not adjusted family-wise guarantees and cannot justify a universal improvement claim from whichever rows happen to pass. The plan explicitly retains all eight, mixed effects and the opposite/inconclusive possibilities. Secondary metrics can expose tradeoffs; they invalidate a comparison only when they show correctness/fairness or exact-claim failure, rather than becoming extra post-hoc primary gates.

Execution must complete both models, all four conditions, both traced setup/preflights, the frozen untraced preflight, the full five-block timing matrices and their native analyses. A partial prefix is incomplete. Every real failure/exclusion/deviation remains retained; changed oracle/protocol requires the affected comparison to rerun rather than a relaxed success criterion.
