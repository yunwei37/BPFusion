## GPU, slot and KV ownership

1. executor/vllm_graph.cu:57-71 consumes every selected row of the completed model/head output, publishes each token followed by a system fence and produced, advances local history, and sets phase2 only after the final token. The combined graph has an explicit body-to-head dependency at157-161. Dispatch launches that graph fire-and-forget and self tail-launches at138-143. The next dispatch cannot consume its output until the previous graph environment and child work complete. NVIDIA's [CUDA12.9.1 graph execution and tail-launch contract](https://docs.nvidia.com/cuda/archive/12.9.1/cuda-c-programming-guide/index.html#tail-launch) supports this ordering. This is a source-based ownership argument; retain the actual graph launch arrangement in the candidate.
2. Current retirement at74-79 publishes one FIFO phase2 slot, clears its local phase and waits for the last published slot to leave DONE. The candidate can instead drain the consecutive phase2 prefix, ending at the first unfinished request. It must consume all rows of the previous graph and set batch0 before release/admission; no graph/input/KV operation from the old request may remain outstanding. Snapshot any release diagnostic identifiers from local records before exposing DONE; never reread released shared-slot fields for instrumentation.
3. bpf/fusion.bpf.c:79-95 atomically reserves the logical sequence and physical bit together before publishing WRITING. A producer paused immediately after the CAS still owns that bit, preventing an eight-slot wrap from stealing its slot. stream_publish:393-399 fills metadata and publishes PENDING. GPU admission:80-97 requires both the next FIFO PENDING and an unused local record. A reservation advanced ahead of PENDING causes admission to wait; it does not authorize consuming FREE/WRITING or skipping the hole.
4. GPU DONE is release of executor use, not producer permission. The producer remains blocked by its reservation until TX has finished all old slot accesses, publishes FREE and atomically clears only that slot's bit. Kernel TX:201-224 and native TX:119-124 implement precisely this boundary. The GPU must neither clear reservation bits nor substitute produced==n_gen for DONE. A new PENDING arriving while the prefix loop is finishing is safe: only the single GPU dispatcher changes local phases, and admission follows release processing.
5. executor/vllm_graph.py:92-100 reserves disjoint per-physical-slot upstream KV banks once. They are held through serving and independent replay and freed only after synchronization at166-167. Neither TX path reads KV. Once the old child graphs and output consumption finish, a new request may overwrite its bank after the ordinary slot admission; old tails remain outside current attention lengths. Waiting for TX reclamation of every other completed slot is not a KV-lifetime requirement. Preserve graph/tensor/block owners and all existing prompt/context bounds.

Therefore the global reclaim wait is redundant for memory ownership under these exact conditions. Per-slot reservation is necessary but is not, by itself, a graph-completion or TCP-ordering guarantee. The existing release/fence/phase/graph/transport rules collectively make prefix publication defensible. Real wrap/reuse qualification remains necessary before claiming the implementation correct.

## TCP behavior

Both paths withhold the final produced token until DONE (kernel155-159; native104-109), including gen1's only token. Keeping this rule prevents a complete reply from prompting reuse while the GPU still owns the slot. Ordinary nonblocking send calls accept/copy bytes into TCP's own storage; slot release is neither peer receipt nor transport ACK. Disconnects can also cause DONE departure. The corrected plan should continue using local reclamation terminology.

Kernel earlier_peer:102-118 blocks a younger response while an earlier pending/DONE request for that peer exists, including physical wrap and partial sends. Kernel partial-header/body accounting and socket references remain unchanged. Native TCP admits at most one outstanding slot per Peer, buffers subsequent request bytes, and admits them only after reply completion. Prefix publication across peers does not remove either ordering mechanism. The candidate does not cure FIFO head-of-line blocking behind an unfinished older GPU request or slow same-peer transmission, and should not claim it does.
